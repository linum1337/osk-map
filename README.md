# ОСК — карта и общая таблица

Код приложения для карты компаний и совместного редактирования. Экспорт: CSV и Excel (.xlsx), с текущими фильтрами. Python/Flask, Gunicorn, SQLite, Leaflet; Docker Compose и Caddy для HTTPS.

## Запуск

1. Скопируйте `.env.example` в `.env`. Укажите DOMAIN, APP_USER и случайный APP_PASSWORD длиной от 16 символов.
2. Направьте домен на VPS, откройте порты 80/443.
3. `docker compose up -d --build`.
4. Откройте HTTPS-адрес и войдите с настроенным логином/паролем.

Без импортированных данных приложение запускается с пустой базой. Рабочие контакты, данные Битрикса, база и пароли в репозитории отсутствуют.

## Перенос данных из готового пакета

Выполните до первого запуска новой установки. Из доверенной резервной копии/пакета перенесите `initial.sqlite3` и `crm-seed.json` в корень. В `app/` перенесите `data.js`, `city-centres.js`, `settlement-coverage.json` и CSV-файлы. **Содержимое прежнего `app/scope.js` скопируйте в `app/scope-data.js`**, чтобы сохранить список скрытых компаний и регионов. Общий `scope.js` из репозитория оставьте на месте. Все перечисленные файлы исключены через `.gitignore`.

Существующая база в Docker volume при обновлении не заменяется. Перенос данных в уже работающую базу требует отдельной миграции. Сохраняйте то же имя папки/Compose-проекта и volumes.

Вместо хранения данных в Git переносите их защищённым каналом или из резервной копии. Не применяйте `git add -f` для исключённых файлов.

## Совместная работа и копии

Отдельные входы администратора и четырёх менеджеров. Обновление таблицы каждые 15 секунд. Версии записей защищают от затирания одновременных правок. Скрытие интерфейсное, авторизованные пользователи API могут прочесть скрытые записи.

`docker compose exec -T app python backup.py > backup.sqlite3` — согласованная копия SQLite. Храните копии вне сервера. Не используйте `docker compose down -v`: он удаляет данные.

Основной процесс работает без root. Сервис `data-init` однократно настраивает права volume. Снимок базы читается immutable/read-only. Прокси рассчитан на один доверенный Caddy из комплекта.

## Excel

В таблице нажмите «Скачать Excel». Выгружаются текущие отфильтрованные строки. Заголовок закреплён, есть автофильтр, перенос текста. Телефоны и другие значения сохраняются строками; содержимое ячеек не интерпретируется как формулы. Сборка XLSX выполняется сервером после проверки роли администратора, без стороннего сервиса.

## Пользователи и права

Администратор входит с существующими `APP_USER` / `APP_PASSWORD` из `.env`. Только этот вход имеет право выгружать таблицу (Excel/CSV) и скачивать статические реестры. У менеджеров кнопки скрыты, прямые обращения к маршрутам выгрузок и файлам CSV/XLSX/ZIP возвращают 403. Это ограничение штатных выгрузок: менеджеры по-прежнему видят и редактируют общую базу и могут вручную копировать видимые данные. Разделение компаний по правам менеджеров здесь не вводилось.

Именные логины менеджеров: `Андрей Логинов`, `Анна Скрынник`, `Светлана Квашина`, `Любовь Коровина`. Регистр и лишние пробелы не важны. Каждому менеджеру выдаётся его собственный пароль. Пароли не хранятся в исходниках; хеши scrypt находятся в таблице `accounts` постоянной базы. Аккаунт с `active=0` не может войти. `.env` сохраняет единственного администратора; импорт не создаёт администраторов.

На существующей установке после обновления кода импортируйте отдельно выданный приватный файл:

```sh
docker compose up -d --build
docker compose exec -T app python manage_users.py import < private-users-import.json
```

Повторный импорт сохраняет пароли существующих пользователей. Приватный JSON и файл паролей не включать в Git и не отдавать менеджерам целиком. Для воспроизводимой проверки прав: `python checks/access.py` в окружении с requirements.txt.

Вход использует стандартный запрос логина/пароля браузера (UTF-8). Чтобы сменить пользователя, откройте отдельный профиль/приватное окно или полностью завершите браузерную сессию с сохранённой HTTP-аутентификацией.

## Единый портал

Главная страница `/` предлагает три направления:

- `/transport/` — исходная транспортная карта: терминалы, маршруты и калькуляторы тарифов.
- `/suppliers/` — карта поставщиков, их складов и филиальных сетей.
- `/companies/` — прежняя карта компаний и общая таблица менеджеров.

Во всех разделах один вход и верхняя навигация. Экспорт по-прежнему только для администратора. Старые прямые запросы к `/api/records` продолжают работать; закладка `/index.html` ведёт на главную.

Код модулей находится в `modules/`. Рабочие данные модулей **не входят в Git**. В полном приватном архиве они лежат в `module-data/transport` и `module-data/suppliers`. При первом запуске приложение копирует недостающие файлы в `/data/modules` постоянного Docker volume. Существующие файлы не заменяются автоматически. Для установки из Git отдельно перенесите папку `module-data` из приватного пакета перед сборкой Docker.

Без этих снимков транспортная и поставщицкая карты открываются без рабочих точек. Начальные геоданные и адресные записи подготовлены в приватном пакете; новые исследования и изменение распределений менеджеров при объединении не выполнялись.

История сравнения тарифов транспортных компаний сохраняет исходное поведение: локальное хранилище браузера. При смене домена старая локальная история автоматически не переносится. Редактирование компаний по-прежнему сохраняется в общей SQLite-базе.

Проверки: `python checks/access.py` и `python checks/portal.py` на временной базе. Эти тесты не изменяют рабочую SQLite и не требуют настоящих паролей менеджеров.

## Страница входа

При открытии портала браузер переходит на `/login`. В выпадающем списке — администратор и четыре менеджера. Значение логина администратора берётся из существующего `APP_USER`, его пароль — из `APP_PASSWORD`; название в списке не даёт роль без верного пароля. Пароли менеджеров не менялись.

После входа используется подписанная cookie-сессия: Secure, HttpOnly, SameSite=Lax. Нужен HTTPS через Caddy из комплекта. Секрет подписи `session.key` создаётся автоматически в постоянном `/data` и не входит в Git. Смена пароля администратора или отключение аккаунта менеджера отзывает соответствующие сессии. Форма защищена CSRF-токеном; переход после входа ограничен страницами портала.

Ссылка «Сменить пользователя» открывает ту же форму. Совместимость API с прежним Basic-входом сохранена, но браузерное окно запроса логина больше не требуется. Проверка формы: `python checks/login.py`.

## Полная выгрузка Excel

Кнопка «Скачать Excel — все данные» экспортирует текущую выборку компаний из рабочей SQLite в согласованном снимке. Лист «Компании» содержит все поля записи: последние сохранённые менеджером телефоны, почту, сайт, статус и заметки, сведения об услугах и адресе, координаты, источники, версию, полные вложенные сведения Битрикс24 (JSON) и будущие дополнительные поля.

Лист «Изменения» содержит всю сохранённую историю выбранных записей: время UTC, логин автора, внесённые значения полей, комментарии и полный объект изменения. Автор теперь записывается сервером из текущей учётной записи. У старых изменений автор не восстанавливается предположением и помечен как незафиксированный. История содержит те изменения, которые ранее были записаны приложением; несохранённый текст в форме в выгрузку не попадает.

Значения длиннее лимита ячейки Excel сохраняются без потерь по частям на дополнительном листе «Длинные значения». Телефоны, исходные нули и формулоподобный текст сохраняются строками. Скрытие компаний и текущие фильтры сохраняются. Доступ к экспорту остаётся только у администратора.

Проверка: `python checks/full_export.py` — менеджер сохраняет две последовательные заметки, администратор получает свежие значения и обе правки с автором; дополнительные поля и длинные Unicode-значения не теряются.

## Запрос в головной офис

В строке клиента и карточке на карте есть действие «Запрос в головной офис». Пользователь добавляет комментарий и подтверждает создание. Сервер копирует актуальную сохранённую запись целиком, её версию, все вложенные данные Битрикс24, историю правок и отдельно записывает автора, время UTC и комментарий запроса. Несохранённый текст формы сначала нужно сохранить в карточке.

Таблица `/requests/` доступна из общей навигации и главной. В ней есть поиск и просмотр всех данных клиента. Снимок фиксируется на момент создания запроса, последующее редактирование исходной карточки не переписывает уже созданный запрос. Клиент остаётся в исходной таблице. Повторный сетевой запрос с тем же ключом не дублирует запись. Это внутренняя таблица портала: сообщений в почту, Битрикс24 или мессенджеры действие не отправляет.

Учётные записи менеджеров и администратора могут создавать и просматривать запросы; Excel с полными снимками и историей выгружает только администратор. Таблица запросов хранится в той же постоянной SQLite и попадает в штатные резервные копии. Проверка: `python checks/head_office.py`.

## Производители в поставщиках

Фильтр «Только производители» включён по умолчанию и запоминается в браузере. Признак берётся из существующей базы: компания считается производителем, если хотя бы одна её точка имеет тип «Производитель». Фильтр сохраняет офисы и склады этой же компании; независимые продавцы и дилеры не включаются по одному упоминанию производства в описании. Он совместим с категорией, регионом, видом точки и переключателями сетей. Проверка: `node checks/manufacturers.cjs`.

## Сверка новой выгрузки Битрикс24

Подготовленный приватный JSON с `format: osk-bitrix-company-import-v1` загружается через кнопку **«Импорт Битрикс24»** в таблице компаний (только администратор). Проверка показывает количество новых компаний, обновлений и смен ответственного. Применение создаёт резервную копию SQLite и выполняет обновление в одной транзакции. Повторный импорт того же файла не создаёт дубли и не сбрасывает последующие пользовательские изменения.

Сопоставление сначала идёт по CRM ID, затем по названию и городу либо точным контактам с согласованным городом. Уже связанные с разными CRM ID карточки автоматически не объединяются. Ответственный берётся из поля компании, а не из автора последнего комментария. Пустые ячейки новой выгрузки не стирают известные контакты. Заполненные в портале контакты, сайт, статус и заметки сохраняются; сведения и комментарии CRM показаны отдельно. Все исходные поля хранятся в `bitrixData`, доступны по кнопке «Все данные Битрикс24» и входят в полный Excel.

Закрытые компании, пометки «убрать», согласованные сетевики и прежние географические ограничения сохраняются. Адреса из CRM не становятся подтверждёнными координатами офиса: если известен город, карта использует явно обозначенный центр города.

Компания, географические отметки и список видимых записей теперь хранятся в постоянной SQLite (`workspace_settings`); исходные приватные файлы используются только для первоначальной настройки. Добавленные импортом компании не исчезают при пересборке контейнера.

CLI для администратора, после обновления кода:

```sh
# Только проверка
docker compose exec -T app python bitrix_import.py < bitrix-import-YYYY-MM-DD.json
# Применение с автоматической резервной копией
docker compose exec -T app python bitrix_import.py --apply < bitrix-import-YYYY-MM-DD.json
```

Сам файл выгрузки/JSON, резервные базы и отчёты сверки не включать в Git. Проверки: `python checks/bitrix_import.py` и `python checks/bitrix_api.py`.

При миграции со старой версии JSON может содержать `workspaceBootstrap` с сохранёнными центрами городов и видимыми ID действующего сайта. Эти настройки применяются только если их ещё нет в постоянной базе. Дополнительный блок не меняет идентичность отчёта для защиты от повторного импорта.

## Деплой на прод из GitHub Actions

Слияние в `main` запускает `.github/workflows/deploy.yml`: раннер заходит по SSH на сервер, делает `git fetch` + `git reset --hard origin/main`, собирает образ через `compose.prod.yaml`, ждёт статус `healthy`, прогоняет smoke-проверки (`/healthz` 200, `/login` 200, `/api/records` без сессии 401) и при неудаче откатывается на предыдущий коммит и пересобирает его. Запуск вручную — вкладка Actions → Deploy production → Run workflow.

Секреты репозитория (Settings → Secrets and variables → Actions):

| Секрет | Значение |
| --- | --- |
| `PROD_HOST` | `193.164.17.141` |
| `PROD_USER` | `root` |
| `PROD_SSH_KEY` | приватный ключ ed25519 без пароля, целиком вместе со строками BEGIN/END |

Перед сборкой workflow делает копию базы в `/root/backups/crm-before-deploy-<дата>.sqlite3`. `.env` и `compose.prod.yaml` не отслеживаются git, поэтому `git reset --hard` их не затрагивает. Репозиторный `compose.yaml` в деплое не используется: он поднимает Caddy и занимает 80/443, где на сервере работает Traefik.


## Дополнение открытых контактов

Администратор передаёт проверенные контакты в `/api/contacts/preview` (проверка) и `/api/contacts/enrich` (применение). Требуются вход администратора и `X-Requested-With: OSK-Map`; проверка Origin сохраняется. Формат: `osk-public-contacts-v1`, дата `checked`, массив `records` с `officeId`, `fields` и `sources`. Для каждого поля нужна ссылка на источник. Разрешены только `website`, `generalPhone`, `email`.

Заполняются только пустые поля. Ручное очищение менеджером сохраняется. Назначения, статусы, заметки, офисные телефоны, координаты, все `bitrix*` и `crm*` поля не меняются. Перед применением создаётся копия SQLite. Изменения записываются в историю, источники сохраняются отдельно в `publicContactSources`, отображаются рядом с контактами и включаются в полную выгрузку. Приватные пакеты с ID клиентов и результатами проверки в Git не включаются.

Проверка: `python checks/contact_enrichment.py`.
